How to read this table
Throughput: Messages processed per second of wall-clock time (higher is better). Median of the runs.
Per CPU-s: Messages processed per second of CPU time (user + system) the whole process used, the median of the runs. A runtime that spins while it waits keeps its cores busy: its wall-clock throughput can look high while each message costs more CPU. This column shows that cost. It includes start-up (a JVM or a BEAM boots in the process too). n/a where the platform's time cannot see the program (Windows).
CPU s: Median CPU seconds (user + system) per run.
Latency: Nanoseconds per message (lower is better). Inverse of throughput.
Memory: Peak resident set size in megabytes, the median of the runs. Includes runtime overhead (JVM ≈ 50 to 100 MB, BEAM ≈ 60 MB, native ≈ 1 to 5 MB). n/a where it cannot be measured.
Tier and #: languages are ranked within their tier (FAIRNESS.md, "Two tiers"). Runtime: the language schedules its own units and owns their mailboxes (unbounded, any sender, failure isolation): Aether, Go, Erlang, Elixir, Pony. Threads + queue: OS threads joined by a queue from the standard library, or the suite's single-producer single-consumer ring where the standard library has none (C, C++, Rust, Zig, Java, Scala). That tier is the floor a runtime is read against, not its competition: on counting, for instance, it measures a hand-written two-thread ring against actor systems.
Relative: Percentage of the fastest throughput in the row's own tier. 100% = fastest of its tier, 50% = half as fast. The bar visualizes this.
CV%: Coefficient of variation (standard deviation ÷ mean × 100). Measures run-to-run stability: ●<5% stable, ●5 to 15% moderate variance, ●>15% noisy (thermal throttling, OS scheduling).
Range: Minimum and maximum throughput observed across all runs. Wider range = less predictable.
Efficiency: Throughput divided by memory (M msg/s per MB). Higher means more work done per unit of memory. Favors lightweight runtimes.
Toolchain: The compiler or runtime version each result came from; hover for the build flags its build file used.
Based on the Savina Actor Benchmark Suite (Imam & Sarkar, Rice University, 2014).
Each language is built by its own build file with its release settings. Every language gets the same warmup runs, then the median of N runs is reported; every run's checksum is verified.
Throughput = operations / wall-clock elapsed (CLOCK_MONOTONIC). Per CPU-s = operations / CPU time (user + system). Memory = peak RSS (/usr/bin/time). CV% = coefficient of variation (σ/μ).
