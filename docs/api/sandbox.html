sandbox

std.sandbox — build a grant list and run code under it.

import std.sandbox

Grants fn

Grants()

new fn

new(name) -> Grants

name: string

A new, empty grant list named `name` (the name is for the reader and for denial logs; it does not change what is allowed). Give it grants in the trailing block; with none it denies everything. Release with free().

enforce fn

enforce(perms, code)

perms: Grants, code: fn

Run `code` with `perms` in force: every sandbox-checked operation inside it, and in anything it calls, must match one of the grants. The grants stop applying when `code` returns. Trusted names: `sandbox.enforce(perms, audit_log, db) callback { ... }`. A call written in the block to a named function (`audit_log(...)`), or into a named module (`db.query(...)`), runs with the authority of the code that wrote the enforce instead of the block's grants. The compiler handles the extra names (compiler/analysis/sandbox_trust.c): it checks them, routes those calls through wrappers, and leaves this two-argument function to do the rest. Trust is lexical and narrow on purpose: - a trusted call's arguments are still evaluated inside the sandbox; - a function called from somewhere else, even one that calls a trusted name, stays sandboxed; - the names cannot be used as values in the block; - only Aether functions can be trusted, not C externs; - an enforce written by contained code records the sandboxed authority it runs under, so trusting a name there gains nothing. The grants are frozen when the block starts: enforce checks against its own copy, which nothing else can reach, so changing `perms` afterwards (or a grant_* call made with it from inside the block, by code it was passed to) does not widen what the running block may do. For the same reason the block is not given the list: its parameter is null. The grants apply to the thread that runs the block, and to every program and library on the same runtime the block calls into on that thread: an export of another library called from inside the block (through a host service, say) is held to these grants too, and an enforce of its own can only narrow them. A message the block sends is handled with no grants, as an actor's thread handles it: also when the send steps an idle receiver of the same core inline, on this thread, since a step puts the thread's levels aside until it ends (#3393). A library built without --shared-runtime on macOS or Windows has a runtime of its own and cannot read these grants: called from inside the block, its checked operations are refused, with a message naming --shared-runtime (docs/containment-sandbox.md).

spawn_socket fn

spawn_socket(perms, prog, argv, env) -> (int, int, string)

perms: Grants, prog: string, argv: ptr, env: ptr

Run `prog` in a child process held to `perms`, with a socket to talk to it: os.run_socket's channel (the child's fd 3, AETHER_IPC_FD=3 and AETHER_IPC_KIND=socket in its env, so std.ipc.parent_channel() finds it) with spawn_sandboxed's containment. Returns (fd, pid, err): the parent's end of the socket and the child's pid, or (-1, -1, reason) with no child started. Reap the child with os.wait_pid(pid) and close fd when done. argv a std.list of the arguments after the program, or null env a std.list of "KEY=VALUE", the child's whole environment, or null for this process's; the sandbox's own variables are added The child starts with libaether_sandbox.so in LD_PRELOAD, checking its libc calls against `perms`, and a kernel layer under it that holds what the preload cannot see (docs/containment-sandbox.md, "Kernel layer"). It fails closed: where the child cannot be contained (macOS, Windows, FreeBSD for now; on Linux, a kernel layer that cannot be set up as asked) it returns an error and starts nothing. Running one uncontained is spawn_socket_uncontained, by name.

spawn_socket_uncontained fn

spawn_socket_uncontained(perms, prog, argv, env) -> (int, int, string)

perms: Grants, prog: string, argv: ptr, env: ptr

spawn_socket with NO sandbox: plain os.run_socket. `perms` is taken and ignored, so a host switches between the two by name and the uncontained one is easy to find in review (grep for spawn_socket_uncontained). For development on a platform spawn_socket refuses, never for a guest that is not trusted.

grant_tcp fn

grant_tcp(_ctx, host, port)

_ctx: Grants, host: string, port: int

Outbound TCP to hosts matching `host` ("db.internal", "*.corp") on `port`, or on any port when `port` is 0. The LD_PRELOAD layer sees only the resolved address, so grant the IP too for code that connects outside std.net.

grant_tcp_listen(_ctx)

Listening for and accepting inbound TCP connections, on any port.

grant_udp fn

grant_udp(_ctx, host, port)

UDP to and from hosts matching `host` on `port`, or any port when 0.

grant_native fn

grant_native(_ctx, path)

Loading native code (dlopen) from paths matching `path`.

grant_fork fn

grant_fork(_ctx)

_ctx: Grants

Starting new processes, in a child spawn_sandboxed starts: fork, vfork, and a clone or clone3 that is not a thread. Without it the child can start threads but no process; the kernel fence refuses the rest.

grant_without_landlock fn

grant_without_landlock(_ctx)

_ctx: Grants

Let sandbox.spawn_socket start the child on a kernel with no Landlock (before Linux 5.13, or with landlock left out of lsm=), held by the preload and seccomp only. Without it spawn_socket refuses there, since a raw syscall (ctypes, a static binary) could then open what the fs grants do not allow. It is a grant so the choice sits in the host's grant list, where a review reads it; it grants the child nothing.
