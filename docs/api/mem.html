copy_at fn

copy_at(dst, dst_off, src, src_off, n) -> ptr

dst: ptr, dst_off: long, src: ptr, src_off: long, n: long

Offset forms of the bulk operations (#1733). The four above can only start at byte 0 of each buffer, and Aether has no pointer arithmetic — so a bulk operation on an INTERIOR span had no spelling at all. Copying one scanline out of a larger framebuffer, or filling a rect's row, meant going byte at a time even though the operation is memcpy-shaped. Contracts match their offset-less twins exactly: a null buffer is a no-op returning `dst` (0 for compare), and offsets are the caller's problem in the same way `n` already is — no range checking is added here, because none exists in the offset-less forms and a bulk primitive that silently clamped would be worse than one that does as it is told. `move_at` matters as much as `copy_at`: an image scrolling within its own buffer is an OVERLAPPING interior copy, so a copy_at-only surface would leave the common case undefined.

compare_slice fn

compare_slice(a, b) -> int

a: byte[], b: byte[]

Lexicographic byte comparison, <0 / 0 / >0 as mem.compare: compares the overlapping prefix (the shorter of the two lengths) first, and if every shared byte matches, the shorter slice sorts first. Two different-length slices are therefore never "equal" even when one is a prefix of the other — check `.len` yourself first if that is the equality you want.

heap_in_use fn

heap_in_use() -> long

The bytes the C allocator has handed out and not taken back: every malloc in the process, Aether's (heap.new, strings, closures, collections) and the ones C code reached through an extern makes, from the allocator's own statistics. -1 where the platform's allocator keeps none (musl), and where the platform's allocator is not the one serving malloc (under valgrind, or with an allocator preloaded in front of glibc's): its statistics would stand still while the program allocates. For a same-process leak check, run the workload a few rounds and compare two later rounds: the growth is what each round leaks. glibc, macOS and jemalloc count freed blocks parked in per-thread caches as in use, and on a churning workload those settle over many rounds, so there a single before/after, or even two rounds, can grow without a leak. heap_in_use_exact() says where the count is exact.

heap_in_use_exact fn

heap_in_use_exact() -> bool

True where heap_in_use() counts exactly the blocks the program holds: Windows (a walk of the process's heaps) and a sanitizer's allocator. Any growth between steady rounds is then a leak. False where it reads an allocator's statistics (glibc, macOS, FreeBSD), under Wine (whose heap walk counts a low-fragmentation group whole) or has no answer: a leak check there belongs to a leak tool (leaks, valgrind, LeakSanitizer).

thread_epoch fn

thread_epoch() -> long

A number that changes whenever a thread starts or ends in the process. On Windows it counts every start and end the loader reports: the program's threads and the ones the system starts in it (a thread-pool worker); and it moves when a thread the loader does not report runs (the parallel loader's workers, whose first run allocates about 1 KB). On Linux, macOS and FreeBSD it is the number of threads, which a start and an end between two reads leave as it was. -1 where the platform gives neither. A thread holds heap blocks of its own while it lives (the OS's and the C runtime's, about 1 KB on Windows), so heap_in_use() moves when one starts, whoever started it.

steady_growth fn

steady_growth(round, tries) -> long

round: fn, tries: int

The growth heap_in_use() shows for one run of `round`, once the work has reached its steady state: `round` is compared up to `tries` times, each run between two reads, and the answer is 0 as soon as one run leaves the count exactly as it found it. A run during which a thread started or ended (thread_epoch) is not compared, and does not use up a try: it is run again, up to 8 such runs in all, so `tries` 1 still compares one run . A leak grows every run, so then the answer is the growth of the last run compared (of the last run, if none could be); a one-time allocation, or a buffer still growing to its high-water mark, lands in some runs and then settles. Meaningful where heap_in_use_exact() is true.
